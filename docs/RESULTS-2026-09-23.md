# Real results — 2026-09-23

Step 4 of the source-value work: run the actual engine (`score_sources`,
`quick_assess` fast + deep, `ablate_sources`, `find_redundant_pairs`,
`greedy_prune`) on a REAL NotebookLM source set, not an offline fake. Everything
below is measured, not assumed — repro script included.

## Setup

- Notebook: a real research notebook (set `NOTELAB_REPRO_NOTEBOOK_ID` to point the
  repro script at your own) — 214 sources at the initial listing, 250 by the time
  the repro script re-ran minutes later (it's a live, actively-growing notebook,
  not a static fixture).
- Subset: 16 sources whose title matches `judge|bias|rater|scoring|evaluat`
  (title-filtered for tractability — full ablation is O(n²); 214² score_sources
  calls over real fetched content is out of scope for a repro-in-minutes report).
  Real content fetched per-source via `nlmx source content <id>` — no synthetic
  text anywhere in this report.
- Two real questions, chosen to contrast a broad phrase against a specific one:
  - **Q1 (broad)**: "LLM-as-a-judge bias mitigation strategies"
  - **Q2 (specific)**: "central tendency bias in clinical ordinal scoring by
    multimodal LLM raters" — deliberately near-quotes one paper's own title, to
    test whether ablation finds the right needle.
- Repro: `python3 scripts/repro_results_2026-09-23.py` (needs a live, authenticated
  `nlmx` on PATH; read-only, fetches the same 16 sources by the same title filter).

## Result 1 — Q1 (broad question)

```
composite = 0.7041
fast: verdict=bloated, coverage=1.0, escalate_to_deep=True
deep: load_bearing=[] (0 of 16), redundant_pairs=11, greedy_prune kept=1 of 16
```

Every one of the 16 sources covers all 5 of the question's terms (`bias`,
`judge`, `llm`, `mitigation`, `strategies`) somewhere in its own text — the
question phrase is generic relative to a topically-coherent corpus that's
*already* all about LLM-as-a-judge bias. Ablation therefore correctly finds
**zero** individually load-bearing sources (removing any one of them doesn't
drop coverage, because 15 others still cover the same 5 terms), and
`greedy_prune` collapses the set to 1 survivor.

This is not a bug — it's the documented lexical-coverage limitation
(`QualityWeights.term_expansions`, `docs/DESIGN.md` "How sparring ranks
families") showing up on real data: these are 16 genuinely different papers
(selection-bias survey vs. clinical central-tendency bias vs. shortcut bias vs.
judge contamination vs...), but a 5-term lexical overlap can't tell them apart.
**This is real evidence motivating Step 5** (a semantic backend behind
`term_expansions`) rather than a synthetic argument for it.

Real duplicate/near-duplicate sources this corpus actually contains (found via
`find_redundant_pairs`, not hand-picked):
- Two imports of the exact same paper, "A Survey on LLM-as-a-Judge" (ids
  `75515782…` / `d0927b58…`) — a genuine re-import duplicate, not just topical
  overlap.
- Three versions (v1/v2/pdf) of "A Systematic Evaluation of Bias Mitigation
  Strategies in LLM-as-a-Judge Pipelines" — same paper, different URLs.

## Result 2 — Q2 (specific question)

```
composite = 0.6466
fast: verdict=good, coverage=1.0, escalate_to_deep=False
deep: load_bearing=['da7a4c3e…'] (1 of 16), redundant_pairs=4, greedy_prune kept=1 of 16
```

Deep ablation correctly isolates **exactly one** load-bearing source:
"Auditing Multimodal LLM Raters: Central Tendency Bias in Clinical Ordinal
Scoring" — the paper the question was written to match. `greedy_prune`'s single
survivor is that same source. On real, noisy, topically-adjacent data, the
engine found the right needle.

## Finding: the fast lane can miss what deep mode catches

Compare the two `fast` verdicts: Q1 says `bloated` (escalate), Q2 says `good`
(no escalate) — yet deep mode shows Q2's set is **just as concentrated**: 15 of
16 sources are redundant, only 1 is load-bearing, identical in kind to Q1.
`quick_assess`'s fast-lane bloated check is
`len(sources) > max(3, 2 * len(qterms))` — it scales with the *number of
question terms*, not with measured redundancy, so a longer/more specific
question (more `qterms`) raises the threshold and can let a heavily redundant
16-source set read as merely "good." A caller trusting `escalate_to_deep` alone
would miss this. **Known limitation, not fixed in this pass** — noted here as
real evidence for a future non-length-based fast-lane redundancy proxy (e.g. a
cheap sampled pairwise check) rather than the current source-count heuristic.

## Golden test

`tests/test_live_results_golden.py` pins the numbers above (against a
size-bounded fixture — same 16 real sources, content truncated to 4000 chars
each, `tests/fixtures/live_notebook_llm_judge_bias.json`) so a future change to
`quality.py`/`ablation.py` that silently shifts scores or verdicts is caught by
the offline test suite, without needing live nlmx access in CI. The truncated
fixture reproduces the same qualitative pattern as the full-content numbers
above (same "broad question → 0 load-bearing" and "specific question → exactly
the right 1 load-bearing" findings), though the exact composite scores differ
slightly from the full-content numbers in this report because of the
truncation.
